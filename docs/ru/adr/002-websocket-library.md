# ADR 002: coder/websocket вместо gorilla/websocket

## Статус
Принято

## Контекст

Для Этапа 3 (real-time синхронизация) нужен WebSocket-хаб: сервер держит
множество соединений, рассылает broadcast-события подписчикам конкретной
доски, поддерживает graceful shutdown через `context.Context`.

vision.md изначально оставлял выбор открытым: "gorilla/websocket или
nhooyr.io/websocket". Открытая развилка в базовом технологическом
документе — плохой знак для демонстрационного проекта: решение влияет на
весь код Этапа 3, и его стоит зафиксировать заранее, а не по ходу
кодирования.

## Рассмотренные варианты

**gorilla/websocket**
- Плюсы: самая большая база знакомого кода и туториалов, 6+ лет в
  проде у множества компаний
- Минусы: репозиторий официально заархивирован в конце 2022 года —
  проект больше не принимает PR и не получает исправлений; API
  предполагает регистрацию pong-хендлера коллбэком (менее наглядный
  control flow); нет нативной интеграции с `context.Context`;
  конкурентная запись в соединение не поддерживается "из коробки" —
  нужен собственный mutex/broadcaster поверх `Conn`

**coder/websocket** (бывший `nhooyr.io/websocket`, в 2024 году передан
под опеку Coder, импортируется как `github.com/coder/websocket`)
- Плюсы: API спроектирован вокруг `context.Context` — `Dial`, `Read`,
  `Close` принимают `ctx`, что естественно ложится на паттерн graceful
  shutdown, который и так используется в остальном проекте (Этап 4);
  поддерживает конкурентную запись без дополнительной синхронизации
  снаружи; работает поверх стандартных `net/http.Client` /
  `http.ResponseWriter` при хендшейке — не дублирует функциональность
  `net/http`, что совпадает с духом ADR 001; активно поддерживается
- Минусы: меньше готовых примеров и Stack Overflow-ответов по
  сравнению с gorilla; часть старых обучающих материалов по Go
  WebSocket всё ещё написана под gorilla, придётся переносить паттерны
  вручную

**gobwas/ws**
- Плюсы: минимальный оверхед, максимальный контроль над буферами,
  ориентирован на event-driven серверы с десятками тысяч соединений
- Минусы: низкоуровневый API, требует самостоятельно реализовать то,
  что coder/websocket и gorilla дают "из коробки" (фреймы, control
  messages, graceful close) — избыточная сложность для pet-проекта,
  где цель — показать хаб/конкурентность, а не написание протокола с
  нуля

## Решение

Используем **`github.com/coder/websocket`**.

## Обоснование

1. Нативная интеграция с `context.Context` напрямую соответствует
   архитектурному выбору Этапа 4 (graceful shutdown всего сервера
   через `context`) — WebSocket-хаб не становится "особым случаем",
   который надо останавливать иначе, чем остальные компоненты
2. gorilla/websocket заархивирован — использование неподдерживаемой
   библиотеки в проекте, демонстрирующем инженерную зрелость, сложно
   обосновать на собеседовании ("почему выбрали библиотеку без
   поддержки?")
3. Конкурентная запись "из коробки" убирает целый класс багов (data
   race на запись в соединение из нескольких горутин broadcast'а),
   которые иначе пришлось бы закрывать вручную — и именно это придётся
   объяснять на собеседовании при вопросе "как вы избегали гонок в
   хабе", так что лучше не тратить объяснение на самописный mutex
   вокруг известной проблемы
4. Совместимость с `net/http.Handler` на хендшейке продолжает линию
   ADR 001 — не подменяет стандартные типы экосистемы

## Последствия

- Handler апгрейда соединения пишется как обычный `http.HandlerFunc`,
  подключается через `chi`-роутер без адаптеров
- Хаб (`internal/realtime/hub.go`) хранит `map[boardID]map[*Client]struct{}`
  под `sync.RWMutex` (или, для будущей демонстрации каналов —
  register/unregister/broadcast через собственные каналы, как и
  запланировано в roadmap.md Этап 3) — сам факт использования
  `coder/websocket` не отменяет задачу спроектировать хаб через
  каналы, это разные уровни абстракции
- Shutdown хаба вызывается из общего `errgroup`/`context.WithCancel`
  сервера — единый механизм остановки для HTTP и WebSocket
- Тесты хаба используют `go test -race`, как и зафиксировано в
  roadmap.md — `coder/websocket` не снимает необходимость тестировать
  конкурентность бизнес-логики хаба, только устраняет гонки на уровне
  самого соединения
- **Heartbeat (ping/pong).** Библиотека не решает за нас, когда считать
  соединение мёртвым — TCP-таймаут ОС может занимать минуты, а клиент
  тем временем "висит" в хабе и получает broadcast в никуда. Каждое
  соединение обслуживается отдельной горутиной с собственным
  `context.WithTimeout`: хаб периодически (например, каждые 30 секунд)
  вызывает `Conn.Ping(ctx)` с таймаутом ожидания pong (например, 10
  секунд). Ключевая деталь: таймаут этого же `ctx` должен отменять и
  блокирующий `Conn.Read(ctx)` в цикле чтения соединения — иначе при
  обрыве связи `Read` останется висеть на сетевом I/O, и горутина
  клиента не завершится, а соединение не будет удалено из хаба
  (утечка горутины). При отмене контекста — закрываем соединение,
  удаляем из хаба, горутина завершается. Это отдельный тест-кейс
  (`TestHub_RemovesDeadConnection`), который стоит явно предусмотреть
  в Этапе 3 — включая проверку, что горутина клиента действительно
  завершилась (например, через `goleak` в тесте)
