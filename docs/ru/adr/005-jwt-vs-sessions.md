# ADR 005: JWT (hand-rolled HS256) вместо серверных сессий

## Статус
Принято

## Контекст

Этап 2 добавляет полноценную регистрацию/логин: нужно решить, как
сервер подтверждает личность пользователя на каждом последующем
запросе. `vision.md` в разделе "Пользователи и роли" явно оставляет
этот выбор за Этапом 2. `openapi.yaml` и контракт сервис-слоя (Этап 1,
все методы принимают `userID uuid.UUID`) уже написаны в расчёте на
последующую замену Stage 1 middleware-заглушки (`DevUserID` в
`internal/transport/http/middleware.go`) новым middleware, кладущим
`userID` в тот же `context.Context` — так что смена механизма
аутентификации не требует правок в domain/service/repository.

## Рассмотренные варианты

**Серверные сессии (session ID в cookie + хранилище на сервере)**
- Плюсы: отзыв токена мгновенный (удалить строку из хранилища), не
  нужно продумывать формат payload
- Минусы: требует отдельного хранилища сессий (Redis либо таблица в
  Postgres) — лишняя инфраструктурная единица ради pet-проекта;
  каждый защищённый запрос требует обращения к этому хранилищу

**JWT через сторонюю библиотеку (`golang-jwt/jwt`)**
- Плюсы: проверенная реализация, поддержка множества алгоритмов и edge
  cases из коробки
- Минусы: скрывает от читателя, что происходит "под капотом" токена —
  тот же аргумент, что и в ADR 001 против full-stack фреймворка: цель
  проекта — показать владение языком и понимание механизма, а не
  скорость интеграции

**JWT, реализованный вручную (HS256, `internal/auth`)**
- Плюсы: не требует нового хранилища (сервер полностью stateless),
  не добавляет зависимостей — подпись/проверка укладываются в
  ~100 строк на `crypto/hmac`/`crypto/sha256`/`encoding/base64`/
  `encoding/json`; формат токена и логика проверки полностью прозрачны
  и покрыты собственными тестами (`internal/auth/jwt_test.go`)
- Минусы: только один алгоритм (HS256) и только проверка `exp` —
  сознательно упрощено относительно full-featured библиотек (нет
  refresh-токенов, `nbf`, ротации ключей); секрет подписи должен быть
  один и тот же на всех инстансах API (нет проблемы для pet-проекта с
  одним инстансом)

## Решение

**JWT (HS256), подпись/проверка реализованы вручную** в
`internal/auth`, без внешней зависимости. Токен без состояния
(stateless): payload — `sub` (userID), `iat`, `exp`; TTL 24 часа,
refresh-токенов нет (осознанно не делаем сложнее — если токен
истёк, пользователь просто логинится заново).

Пароли хранятся как bcrypt-хэш (`golang.org/x/crypto/bcrypt`, уже был
транзитивной зависимостью через pgx) — в колонке `users.password_hash`,
которая существовала в схеме с Этапа 1 (см. `architecture.md`,
"Заглушка пользователя на Этапе 1").

На фронтенде токен хранится в `localStorage` (в проекте нет
стейт-менеджера, это самый простой вариант, согласующийся с
минималистичным стилем `web/`). Компромисс: `localStorage` доступен
любому JS на странице (XSS), в отличие от httpOnly cookie — для
pet-проекта без пользовательского контента, который мог бы стать
вектором XSS, это приемлемо; для продакшена стоило бы пересмотреть в
пользу httpOnly cookie + CSRF-защиты.

Для WebSocket-хендшейка (`GET /boards/{boardId}/ws`) браузерный API
`WebSocket` не позволяет выставить заголовок `Authorization` — токен
передаётся через query-параметр `?token=`. Middleware `JWTAuth`
проверяет сначала заголовок, затем query-параметр.

`DevUserID` и заголовок `X-User-ID` (заглушка Этапа 1) полностью
удаляются, а не остаются как альтернативный механизм — см. roadmap.md,
Этап 2: новый middleware "заменяет" заглушку.

## Обоснование

1. Тот же принцип, что и в ADR 001: pet-проект для демонстрации
   инженерного мышления выигрывает от прозрачного, объяснимого кода
   больше, чем от готовой библиотеки — здесь это перевешивает
   стандартный аргумент "не изобретай велосипед для крипто-кода",
   поскольку формат JWT простой, а корректность (constant-time
   сравнение подписи через `hmac.Equal`, проверка `exp`) закрыта
   тестами
2. Stateless-токен не требует нового хранилища и держит сервер без
   состояния между запросами — согласуется с тем, что сервис уже не
   хранит никакого server-side состояния сессии
3. bcrypt даётся "бесплатно" (уже в зависимостях через pgx)

## Последствия

- Отозвать токен до истечения `exp` невозможно (нет чёрного списка) —
  осознанно не реализуем; при компрометации секрета единственный выход
  — сменить `JWT_SECRET`, что инвалидирует все выданные токены разом
- Смена подписи (`JWT_SECRET`) требует передачи через переменную
  окружения (см. `cmd/api/main.go`, `os.Getenv("JWT_SECRET")`,
  fallback только для локальной разработки с явным `slog.Warn`)
- Если в будущем понадобится отзыв токенов, множественные инстансы API
  с независимой ротацией ключей или refresh-токены — потребуется
  отдельный ADR с пересмотром решения
