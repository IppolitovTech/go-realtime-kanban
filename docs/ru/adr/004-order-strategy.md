# ADR 004: float (double precision) вместо строкового LexoRank для order

## Статус
Принято

## Контекст

Column и Card хранят порядок (`order`) в рамках родителя (доски —
для колонок, колонки — для карточек). Порядок меняется пользователем
через drag-n-drop, потенциально конкурентно с другими участниками
доски (см. use case 7 в vision.md — несколько вкладок одновременно).

Наивный целочисленный `order` (0, 1, 2...) требует пересчёта соседних
записей при каждой вставке между двумя существующими — O(n) обновлений
в худшем случае и источник гонок при конкурентных перемещениях.
Решение зафиксировано отдельно от ADR 001-003, так как влияет на схему
БД, а не на транспортный/инфраструктурный слой.

## Рассмотренные варианты

**Целочисленный `order` с пересчётом соседей**
- Плюсы: тривиально для понимания, `ORDER BY order_num`
- Минусы: вставка между двумя карточками требует транзакционного
  обновления всех записей после точки вставки — O(n) UPDATE-ов,
  дорого и создаёт окно для гонок при конкурентном перемещении

**Строковый лексикографический индекс (LexoRank, как в Jira)**
- Плюсы: вставка — всегда одна операция (O(1)), не заканчивается
  "местом" между соседями, потому что между любыми двумя строками
  всегда можно сгенерировать промежуточную
- Минусы: требует реализовать генератор промежуточных ключей
  (base62-алфавит, инкремент/деление "посередине" между строками),
  плюс фоновую ребалансировку через bucket-схему, когда строки
  дорастают до предельной длины — заметный объём кода и логики,
  которую придётся объяснять и тестировать отдельно от бизнес-логики
  доски. Для масштаба pet-проекта это сложность ради сложности:
  демонстрирует умение реализовать LexoRank, а не архитектурное
  мышление про сам trade-off

**float / `double precision` с локальной перенумерацией (как в Trello)**
- Плюсы: вставка между двумя карточками — среднее арифметическое их
  `order` (`(a + b) / 2`), почти всегда одна операция; реализация в
  несколько строк, без дополнительных зависимостей и генераторов
  ключей; `double precision` в PostgreSQL имеет ~15-17 значащих
  десятичных цифр — с запасом для сотен перемещений между одной и той
  же парой соседей, прежде чем точность станет проблемой
- Минусы: точность double не бесконечна — при очень частых вставках
  между одной и той же парой карточек разница между соседними `order`
  в какой-то момент схлопывается до нуля (`(a+b)/2 == a` из-за
  округления). Требуется явный fallback: детектировать это состояние
  и перенумеровать локальный участок списка (не всю доску)

## Решение

Используем **`double precision`** с шагом ~1000 между соседними
элементами при первичной вставке (например, 1000, 2000, 3000...) и
локальной перенумерацией при схлопывании точности — по модели Trello.

## Обоснование

1. Соответствует ADR 001: минимум зависимостей и "магии", максимум
   явного, объяснимого кода — та же логика, что предпочла
   `net/http+chi` вместо Gin и `sqlc` вместо ORM
2. Реализация укладывается в service-слой без отдельной библиотеки:
   `NewOrderBetween(prev, next *float64) float64`, легко покрывается
   табличными тестами (в том числе edge-кейс схлопывания точности —
   хороший повод показать умение тестировать граничные случаи)
3. Проверено на практике в проде сопоставимого масштаба и сложности
   задачи (Trello) — не экспериментальное решение
4. Полноценный LexoRank добавляет объём кода (парсер/генератор строк,
   bucket-ребалансировка), который для демонстрационного проекта не
   несёт дополнительной архитектурной ценности сверх того, что уже
   показывает более простая реализация с тем же trade-off

## Конкурентная запись `order_num`

`id`-tiebreaker в `ORDER BY order_num, id` решает только
детерминированность **отображения** — если два `order_num` совпали,
рендер стабилен. Он не решает отдельную проблему: гонку на **чтении
соседей**. Между тем, как транзакция A прочитала `order_num` соседей
`prev`/`next`, и тем, как она записала вычисленный midpoint, другая
транзакция могла успеть сдвинуть один из этих соседей — тогда
midpoint вычислен по устаревшим данным, и вставленная карточка может
оказаться вне ожидаемого диапазона (нарушение инварианта
`order_prev < order_num < order_next`).

Решение: операция перемещения карточки — это одна транзакция,
берущая **advisory lock на уровне колонки**
(`pg_advisory_xact_lock(column_id)` — или `board_id` для колонок)
перед чтением соседей. Лок держится до конца транзакции и
автоматически снимается при commit/rollback (`_xact_`-вариант, не
требует явного unlock). Все операции перемещения внутри одной колонки
сериализуются; операции в разных колонках/досках выполняются
конкурентно без блокировки друг друга.

Альтернатива — `SELECT ... FOR UPDATE` на конкретные строки-соседи —
была рассмотрена и отклонена: требует заранее корректно определить,
какие именно строки лочить, что само по себе гонка (соседи могли
измениться до `SELECT`), тогда как advisory lock на колонку исключает
проблему на уровне "входа" в критическую секцию, а не пытается
угадать нужные строки. Для ожидаемого масштаба конкурентности в
pet-проекте (несколько открытых вкладок на одной доске, не тысячи
одновременных пользователей) полная сериализация перемещений внутри
колонки не создаёт заметной задержки.

## Последствия

- Схема: `column.order_num DOUBLE PRECISION NOT NULL`,
  `card.order_num DOUBLE PRECISION NOT NULL`, уникальность не
  требуется (сортировка `ORDER BY order_num, id` — `id` как
  тай-брейкер на случай редкой коллизии значений)
- Service-слой при вставке/перемещении: открывает транзакцию → берёт
  `pg_advisory_xact_lock(column_id)` → читает актуальных соседей →
  вычисляет `order_num` как среднее между ними → если
  `math.Abs(next-prev) < epsilon` (порог схлопывания, например
  `1e-6`) — выполняет локальную перенумерацию окна карточек вокруг
  точки вставки с шагом 1000 → commit
- Тест-кейс на service/repository-слое, явно проверяющий
  перенумерацию при схлопывании точности — обязательная часть
  Этапа 1
- Отдельный интеграционный тест на конкурентные перемещения внутри
  одной колонки (несколько горутин одновременно вызывают move) —
  проверяет, что итоговый порядок не нарушает инвариант
  `prev < order_num < next` ни для одной карточки — обязательная
  часть Этапа 1, наравне с `go test -race` для WS-хаба в Этапе 3
- Если в будущем понадобится избавиться даже от редкой локальной
  перенумерации (например, при кратно большем масштабе конкурентных
  правок) — потребуется отдельный ADR о переходе на LexoRank, по
  аналогии с оговоркой в ADR 001 про fasthttp

## Путь эскалации (не реализуется сейчас, только зафиксирован)

Advisory lock на колонку сериализует все перемещения внутри неё — при
низкой конкурентности (несколько вкладок) это незаметно, но при
кратном росте одновременных пользователей на одной колонке станет
узким местом. Сознательно не реализуется сейчас: добавило бы retry-логику,
version-поле и заметно менее детерминированные тесты без реальной
необходимости при текущем масштабе — тот же принцип "не усложнять
раньше времени", что и в ADR 001/003/004 в целом.

Если/когда это понадобится, эскалация в два шага:

1. **Optimistic concurrency (CAS с retry)** вместо pessimistic lock —
   читаем соседей без блокировки, пишем через условный `UPDATE`,
   проверяющий, что соседи не изменились с момента чтения; при
   конфликте — retry. Не блокирует остальных писателей, эффективен
   при низкой вероятности коллизии (конкретная пара соседей меняется
   редко даже при большом числе пользователей на доске)
2. **Перенос генерации ключа на клиента** (тогда уже оправдан переход
   на LexoRank/fractional indexing) — клиент генерирует order локально
   без round-trip к серверу за блокировкой, конфликты разрешаются
   tie-breaker'ом при чтении, ценой периодической фоновой
   ребалансировки — подход, аналогичный collab-движку Figma
