# ADR 003: sqlc вместо ручного database/sql или ORM

## Статус
Принято

## Контекст

Repository-слой (Этап 1) должен читать/писать User, Board, Column, Card
в PostgreSQL. vision.md изначально оставлял открытым выбор между
"sqlc/database-sql" — то есть саму стратегию работы с БД, а не только
конкретную библиотеку. Это напрямую определяет форму
`internal/repository`: раздельно генерируемый код или ручные
`Scan`/`Exec`.

## Рассмотренные варианты

**Ручной `database/sql`**
- Плюсы: максимально explicit — каждый `Scan` виден в коде, ничего не
  генерируется "магией"; ноль дополнительных зависимостей в toolchain
- Минусы: много повторяющегося boilerplate на каждый метод репозитория
  (`rows.Scan(&a, &b, &c, ...)`); при добавлении колонки в таблицу
  легко забыть обновить один из Scan-ов — компилятор не поймает
  несовпадение количества полей до рантайма; ручное построение
  запросов с опциональными фильтрами быстро превращается в
  string-конкатенацию или громоздкий query-builder

**ORM (например, GORM, ent)**
- Плюсы: быстрое прототипирование, автоматические миграции,
  relationship-loading "из коробки"
- Минусы: часть SQL скрыта за ORM-абстракцией — на собеседовании
  сложнее показать понимание реальных запросов и их производительности
  (N+1, индексы, план выполнения); ent генерирует собственный
  query-builder API, что снова уводит от "стандартного" Go-подхода —
  та же логика, что уже отвергла Gin в пользу net/http в ADR 001

**sqlc**
- Плюсы: пишете обычный SQL руками (`.sql`-файлы с запросами) —
  полный контроль и видимость запроса, как в ручном `database/sql`;
  sqlc генерирует типобезопасные Go-функции и структуры из этого SQL
  на этапе `go generate`, так что несовпадение колонок/типов ловится
  на компиляции, а не в рантайме; сгенерированный код — это тонкая
  обёртка над `database/sql`/`pgx`, а не собственный рантайм-слой —
  легко объяснить на собеседовании "вот SQL, вот что из него
  сгенерировано"; хорошо сочетается с `golang-migrate`, который уже
  выбран в vision.md — миграции и запросы остаются в чистом SQL
- Минусы: дополнительный шаг генерации кода в workflow (`sqlc generate`
  перед сборкой, требует CI-шаг); чуть менее гибко для сильно
  динамических запросов (опциональные фильтры на лету) — такие места
  приходится писать вручную поверх `pgx`, а не через sqlc

## Решение

Используем **sqlc** поверх драйвера **`pgx`** (`github.com/jackc/pgx/v5`)
как низкоуровневого драйвера PostgreSQL.

## Обоснование

1. sqlc сохраняет ту же философию, что и ADR 001: минимум "магии",
   максимум видимости происходящего — запрос, который выполняется,
   написан явно на SQL и лежит в репозитории, а не собран рантайм-ORM
2. Типобезопасность на этапе компиляции — конкретное демонстрируемое
   инженерное решение проблемы "рассинхронизации схемы и кода", которую
   легко объяснить и обосновать на собеседовании
3. `golang-migrate` (уже в стеке) отвечает за DDL/схему, sqlc — за DML;
   разделение ответственности чистое, оба инструмента работают с одним
   и тем же `.sql`-source of truth
4. `pgx` — самый быстрый и функционально полный PostgreSQL-драйвер для
   Go, поддерживает нужные для Этапа 5 (optimistic locking через
   version-field) возможности транзакций и `RETURNING`-конструкций
   без обёрток

## Последствия

- Структура: `internal/repository/postgres/queries/*.sql` (source),
  `internal/repository/postgres/generated/*.go` (sqlc output, не
  редактируется руками, коммитится в репозиторий для воспроизводимости
  сборки)
- Repository-интерфейсы в `internal/repository` (например,
  `BoardRepository`) остаются ручными Go-интерфейсами, которые
  оборачивают сгенерированный sqlc-код — это даёт точку для моков в
  service-слой тестах (табличные тесты на service, зафиксированные в
  roadmap.md Этап 1, продолжают работать через интерфейс, не завися от
  sqlc)
- CI-шаг: `sqlc generate --dry-run` или проверка `git diff` после
  генерации — чтобы поймать забытый `sqlc generate` перед коммитом
- Динамические/опциональные фильтры (если появятся, например поиск
  карточек по нескольким необязательным полям) пишутся вручную через
  `pgx` builder-паттерн — явно документируется на месте, а не
  предполагается по умолчанию для всех запросов
- **Сгенерированные sqlc-структуры (`generated.Card`, `generated.Board`
  и т.п.) не покидают `internal/repository/postgres`.** Repository-
  интерфейсы (`BoardRepository`, `CardRepository`...) в своих сигнатурах
  оперируют только domain-моделями из `internal/domain`; маппинг
  `generated.X` → `domain.X` — явная функция внутри реализации
  репозитория, а не общий/рефлективный конвертер. Если sqlc-тип
  просочится в service или transport — это нарушение границы слоёв,
  которую и должен демонстрировать проект (см. engineering goals в
  vision.md, "явная архитектура, а не спрятанная магия")
