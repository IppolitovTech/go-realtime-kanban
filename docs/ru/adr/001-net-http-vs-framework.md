# ADR 001: net/http + chi вместо full-stack фреймворка (Gin/Echo/Fiber)

## Статус
Принято

## Контекст

Для HTTP-слоя backend нужно выбрать между:
1. Полноценным Go-фреймворком (Gin, Echo, Fiber)
2. Стандартной библиотекой `net/http` + тонким роутером (chi, gorilla/mux)

Проект — pet-проект для демонстрации навыков Go-разработчика при
трудоустройстве, а не коммерческий MVP с жёстким дедлайном.

## Рассмотренные варианты

**Gin / Echo**
- Плюсы: быстрее писать хендлеры, встроенные binding/validation для JSON,
  большое комьюнити, много туториалов
- Минусы: собственный `Context`-тип вместо стандартного `http.Handler`,
  часть логики (binding, middleware chain) скрыта "под капотом" —
  сложнее показать понимание того, что происходит на уровне HTTP

**Fiber**
- Плюсы: очень высокая производительность (построен на fasthttp),
  Express-подобный API
- Минусы: fasthttp не совместим с интерфейсом `net/http`
  (`http.Handler`, `http.ResponseWriter`), из-за чего часть стандартных
  библиотек и мидлвар Go-экосистемы не работает без адаптеров

**net/http + chi**
- Плюсы: хендлеры — обычные `func(w http.ResponseWriter, r *http.Request)`,
  узнаваемые любым Go-разработчиком; chi добавляет только роутинг,
  группировку роутов и middleware chain, не подменяя стандартные типы;
  явно видно, как работает routing/middleware/context propagation
- Минусы: чуть больше boilerplate по сравнению с Gin (например, ручной
  JSON encode/decode вместо `c.BindJSON`)

## Решение

Используем **`net/http` (стандартная библиотека) + `chi`** для роутинга.

## Обоснование

1. Go-комьюнити и большинство вакансий ценят владение idiomatic Go и
   стандартной библиотекой выше, чем знание конкретного стороннего
   фреймворка — сам язык спроектирован по принципу "batteries included,
   минимум магии"
2. chi остаётся тонкой прослойкой над `net/http`: хендлеры пишутся через
   стандартный интерфейс `http.Handler`, что упрощает объяснение
   архитектуры на собеседовании и совместимо с любыми стандартными
   мидлварами Go-экосистемы
3. Цель проекта — показать инженерное мышление и владение языком,
   а не скорость поставки фичи; скрытая "магия" фреймворка работает
   против этой цели
4. Разница в скорости написания CRUD-хендлеров (Gin vs net/http+chi)
   несущественна в масштабах pet-проекта и не окупает потерю
   демонстрационной ценности

## Последствия

- Чуть больше ручного кода на JSON encode/decode и валидацию запросов —
  компенсируется собственным небольшим helper-слоем (`internal/transport/http/respond.go`)
- Любой middleware пишется как стандартный `func(http.Handler) http.Handler` —
  переносим между проектами без адаптации
- Если в будущем понадобится fasthttp-производительность — потребуется
  отдельный ADR с пересмотром решения
