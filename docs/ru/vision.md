# Kanban Board — Vision

## Что это

Многопользовательская Kanban-доска с real-time синхронизацией между участниками.
Backend на Go, frontend на React (готовый UI-компонент для drag-n-drop + свой слой поверх него).

*Идеи по дальнейшему расширению (сбор вакансий, AI-классификация и т.п.)
вынесены за пределы этого документа — см. `future-ideas.md`. Это не
часть заявленной цели проекта, а список идей "на будущее", чтобы не
создавать скоуп-крип.*

## Зачем этот проект

Это pet-проект для демонстрации навыков перед техническим собеседованием
на позицию Go-разработчика. Вместо очередного CRUD-тудушника выбрана
Kanban-доска с real-time синхронизацией — она естественно требует
показать то, что сложно продемонстрировать на простом примере:
конкурентный доступ к общему состоянию (WebSocket-хаб, в который
одновременно пишут несколько горутин), явную слоистую архитектуру
вместо логики "всё в одном хендлере", и работу с БД в условиях, где
возможны гонки при конкурентном изменении порядка карточек.

### Инженерные принципы (engineering goals)

Важно не просто "фичи работают", а что именно должно быть верно про
код на любом этапе:

- **Конкурентность без гонок** — весь код, работающий с общим
  состоянием (WS-хаб, worker pool), покрыт тестами с `go test -race`;
  отсутствие гонок — не предположение, а подтверждённый факт
- **Явная архитектура, а не спрятанная магия** — каждый слой
  (domain/service/repository/transport) не знает о деталях соседних
  слоёв; зависимость от конкретной библиотеки (роутер, БД-драйвер,
  WebSocket) ограничена transport/repository-слоем и не протекает в
  domain/service
- **Осознанные решения, а не дефолты по инерции** — каждая
  нетривиальная развилка (роутер, WebSocket-библиотека, стратегия
  работы с БД, order-стратегия) зафиксирована в ADR с рассмотренными
  альтернативами, а не выбрана "потому что все так делают"
- **Ошибки и graceful degradation обрабатываются явно** — единая
  стратегия маппинга ошибок domain → HTTP, graceful shutdown всего
  сервера и фоновых воркеров, а не голый `os.Exit`/паника

## Пользователи и роли

**В MVP — одна роль**, без разграничения прав: любой участник доски
может создавать/двигать/редактировать карточки и колонки, приглашать
других пользователей, удалять доску. `Board.owner_id` (создатель)
фиксируется в схеме с самого начала, но никак не влияет на доступные
действия до отдельного этапа в конце roadmap.md.

Целевая модель ролей (реализуется отдельным опциональным этапом,
см. roadmap.md, Этап 6):

| Роль | Что может делать |
|---|---|
| Владелец доски | создаёт доску, приглашает участников, удаляет доску |
| Участник доски | создаёт/двигает/редактирует карточки и колонки |
| Гость (не авторизован) | не имеет доступа — авторизация обязательна |

*Про то, как `userID` передаётся через слои до появления полноценной
авторизации в Этапе 2 — см. `architecture.md`.*

## Основные сущности (domain model)

- **User** — пользователь системы (email, имя, пароль; способ аутентификации фиксируется в ADR к Этапу 2)
- **Board** — доска (принадлежит владельцу, имеет список участников)
- **Column** — колонка на доске (например: To Do / In Progress / Done), имеет порядок
- **Card** — карточка задачи внутри колонки (заголовок, описание, порядок, автор)
- **BoardMember** — связь User ↔ Board (кто состоит на доске)

*Стратегия хранения `order` — float с локальной перенумерацией
(по модели Trello), зафиксировано в ADR 004 — см. `architecture.md`
для контекста проблемы.*

*Метки/теги на карточках — не часть MVP-модели, добавляются опционально
в Этапе 5 (см. `roadmap.md`); сознательно не включены в список выше,
чтобы не создавать впечатление обязательного MVP-поля.*

## Ключевые сценарии использования (use cases)

*"MVP" здесь — это сумма Этапов 0-3 из `roadmap.md` (скелет → CRUD →
авторизация → real-time), а не один этап. В частности, Этап 1 в
roadmap сознательно реализует CRUD **без** авторизации — это
промежуточный, а не финальный срез MVP; логин, приглашения и real-time
из списка ниже появляются только в Этапах 2-3.*

### MVP (обязательно для первой версии)
1. Пользователь регистрируется / логинится
2. Пользователь создаёт доску
3. Пользователь создаёт колонки на доске
4. Пользователь создаёт карточку в колонке
5. Пользователь перемещает карточку между колонками (drag-n-drop на фронте → PATCH на бэке)
6. Пользователь приглашает другого пользователя на доску
7. **Несколько пользователей одновременно открывают одну доску — изменения одного видны другому в реальном времени без перезагрузки страницы**

### Фаза 2 (после MVP)
8. Разрешение конфликтов при одновременном редактировании одной карточки
9. Уведомления (например, "карточка назначена на вас")
10. Фоновая обработка (worker pool) — основа для будущего парсинга вакансий

## Что НЕ входит в проект (сознательно исключено)

- Мобильное приложение — только web
- Сложная система прав доступа (RBAC с гранулярными правами) — не нужна для демонстрации Go-скиллов
- Кастомный UI-кит / дизайн-система — используется готовый React drag-n-drop компонент
- Масштабирование на множество серверов / кластер — pet-проект рассчитан на single-instance

## Технологический стек (кратко)

- **Backend**: Go, chi (роутинг, см. ADR 001), `coder/websocket` для real-time (см. ADR 002), PostgreSQL + sqlc + pgx (см. ADR 003), golang-migrate
- **Frontend**: React, dnd-kit, Tailwind CSS, обычный fetch/WebSocket клиент
- **Инфраструктура**: Docker Compose (app + Postgres), GitHub Actions (тесты + `go test -race` в CI)

*Про разделение ролей REST (команды) и WebSocket (push-уведомления) —
см. `architecture.md`.*

*Подробности архитектуры — см. `architecture.md`, REST API —
`openapi.yaml`, решения — `adr/`. Отдельного файла со схемой БД пока
нет: до Этапа 0 её не существует физически, а после — source of truth
это SQL-миграции в `internal/repository/postgres/migrations`
(golang-migrate, см. ADR 003), а не отдельный markdown-документ,
который придётся синхронизировать вручную.*
