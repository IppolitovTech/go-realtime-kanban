# Kanban Board — Roadmap

Поэтапный план разработки. Каждый этап должен заканчиваться рабочим,
проверяемым результатом (можно запустить и увидеть/потрогать), а не
"написал код, но пока не собирается".

Порядок специально выстроен так, чтобы как можно раньше получить
end-to-end работающую вертикаль (фронт → бэк → БД), а потом наращивать
функциональность вширь.

---

## Этап -1 — Технические решения до старта кодирования
**Цель:** закрыть развилки, которые в vision.md изначально были
оставлены как "или" (`gorilla/websocket или nhooyr.io/websocket`,
`sqlc/database-sql`). Открытые развилки в базовом техническом
документе — риск: решение, принятое "по ходу" в середине Этапа 1 или 3,
заставляет переписывать уже написанный код.

- [x] ADR 002 — выбор WebSocket-библиотеки (`adr/002-websocket-library.md`)
- [x] ADR 003 — стратегия работы с БД (`adr/003-database-strategy.md`)
- [x] ADR 004 — стратегия хранения `order` у колонок/карточек (`adr/004-order-strategy.md`) — float с локальной перенумерацией, по модели Trello

**Результат:** три ADR в `adr/`, на которые Этап 0+ ссылается без
"додумывания на ходу".

## Этап 0 — Скелет проекта
**Цель:** пустой, но полностью настроенный проект, который можно запустить.

- [ ] Инициализировать Go-модуль, структура папок (`cmd/`, `internal/domain`, `internal/service`, `internal/repository`, `internal/transport/http`)
- [ ] Базовый HTTP-сервер на chi + `GET /health` (заглушка `{"status":"ok"}`) + helper для JSON-ответов (`respond.go`)
- [ ] Поднять Postgres в Docker Compose
- [ ] Подключение к БД из Go через `pgx` (расширить `/health` — проверка соединения с БД) — см. ADR 003
- [ ] Настроить golang-migrate, первая пустая миграция
- [ ] Настроить sqlc (`sqlc.yaml`, пустой `queries/`-каталог, `go generate` в Makefile) — см. ADR 003
- [ ] Единый Makefile-таск (`make db-sync` или аналог: `migrate up && sqlc generate`), чтобы схема Postgres и сгенерированный sqlc-код не расходились ни локально, ни в CI
- [ ] `vision.md`, `roadmap.md`, `adr/` в репозитории
- [ ] Базовый README (как запустить)

**Результат:** `docker compose up` → `curl localhost:8080/health` → `{"status":"ok"}`

## Этап 1 — CRUD без авторизации (одна вертикаль целиком)
**Цель:** доска/колонки/карточки работают end-to-end, включая фронт.

**Контракт с самого начала.** Даже до появления настоящей авторизации
(Этап 2) все методы service-слоя принимают `userID uuid.UUID` явным
параметром. В Этапе 1 хендлер временно подставляет константу/заглушку
вместо значения из токена. Так Этап 2 меняет только транспортный слой
(появляется middleware, кладущий реальный `userID` в `context`), а
domain/service/repository не переписываются задним числом.

- [ ] Domain-модели: User (заглушка), Board, Column, Card — order-поле
      реализовано согласно ADR 004
- [ ] Repository-слой для Board/Column/Card: sqlc-запросы в
      `internal/repository/postgres/queries/*.sql` + ручные Go-интерфейсы
      поверх сгенерированного кода (интерфейсы — точка для моков в тестах)
- [ ] Service-слой с базовой бизнес-логикой (например, порядок колонок/карточек), сигнатуры методов принимают `userID`
- [ ] Тест-кейс на схлопывание точности `order` и локальную перенумерацию (см. ADR 004) — обязательная часть, не опциональная
- [ ] Интеграционный тест на конкурентные перемещения карточек внутри одной колонки (несколько горутин, реальная БД) — проверка, что advisory lock защищает инвариант `prev < order_num < next` (см. ADR 004)
- [ ] Единая стратегия маппинга domain-ошибок в HTTP-статусы: sentinel-ошибки
      (`ErrBoardNotFound`, `ErrNotBoardMember` и т.п.) в domain-слое →
      `errors.Is/As` в transport-слое → маппинг в `respond.go`
      (404/403/400/500), а не ad hoc обработка в каждом хендлере
- [ ] REST-хендлеры: создать/получить/обновить/удалить доску, колонку, карточку
- [ ] Табличные тесты на service-слой (с in-memory моком репозитория)
- [ ] Найти/подготовить React drag-n-drop шаблон (@hello-pangea/dnd или dnd-kit)
- [ ] Убрать моковые данные шаблона, подключить к REST API (fetch/axios-клиент)
- [ ] Реализовать вызовы: получить доску со списком колонок и карточек, создать доску/колонку/карточку
- [ ] Перемещение карточки (drag-n-drop на фронте → `PATCH /cards/{id}/move` на бэке)

**Результат:** можно создать доску в браузере, добавить колонки, карточки, подвигать их — данные сохраняются в Postgres.

## Этап 2 — Авторизация
**Цель:** доски привязаны к реальным пользователям.

- [ ] Регистрация / логин (JWT или сессии — выбрать и зафиксировать в ADR)
- [ ] Middleware авторизации на защищённых эндпоинтах — кладёт реальный
      `userID` в `context`, заменяя заглушку из Этапа 1 (сигнатуры
      service-методов не меняются)
- [ ] Привязка Board → owner_id (создатель доски фиксируется в схеме,
      но не даёт особых прав в MVP — см. vision.md, "Пользователи и роли")
- [ ] Приглашение участника на доску (BoardMember) — любой участник
      может пригласить, разграничения "кто может приглашать" нет в MVP
- [ ] Фронт: экран логина/регистрации, хранение токена

**Результат:** без логина доски не видно; разные пользователи видят только свои/приглашённые доски.

## Этап 3 — Real-time (WebSocket)
**Цель:** несколько открытых вкладок видят изменения друг друга без перезагрузки.

- [ ] Спроектировать формат событий (новый файл `docs/ru/websocket-events.md` — OpenAPI 3.0 не описывает WS-каналы, поэтому события фиксируются отдельным markdown-документом, а не в `openapi.yaml`)
- [ ] WebSocket-хаб на `coder/websocket` (см. ADR 002): register/unregister/broadcast каналы
- [ ] Heartbeat (ping/pong): периодический `Conn.Ping(ctx)` + таймаут ожидания pong → удаление "мёртвого" соединения из хаба (см. ADR 002)
- [ ] Подключение клиента к хабу при открытии доски
- [ ] При каждом REST-изменении (создание/перемещение карточки) — рассылка события всем клиентам доски
- [ ] Graceful shutdown хаба через `context.Context`, единый с shutdown HTTP-сервера
- [ ] Тест хаба с `go test -race` — обязательно без гонок, включая проверку удаления "мёртвого" соединения по heartbeat-таймауту
- [ ] Фронт: подписка на WebSocket, применение входящих событий к состоянию

**Результат:** открываете доску в двух вкладках браузера — двигаете карточку в одной, она сама двигается во второй.

## Этап 4 — Устойчивость и качество
**Цель:** проект выглядит production-ready, а не студенческой поделкой.

- [ ] Structured logging (`log/slog`)
- [ ] `net/http/pprof` подключен для живой отладки горутин/памяти работающего сервиса — актуально при отладке WS-хаба с открытыми соединениями
- [ ] Graceful shutdown всего сервера (SIGTERM → доработать активные запросы/соединения)
- [ ] Обработка ошибок и таймаутов (`context.WithTimeout` на все внешние вызовы)
- [ ] Базовые метрики (prometheus/client_golang) — опционально, если останется время
- [ ] Покрытие тестами критичных мест, `go test -race ./...` в CI
- [ ] GitHub Actions: линт + тесты на каждый PR (включая `sqlc generate --dry-run`/проверку `git diff`, см. ADR 003)
- [ ] `architecture.md` с диаграммой (Mermaid) — финализировать под фактическую реализацию

**Результат:** зелёный CI на GitHub, `docker compose up` поднимает всё с нуля, сервис не падает при Ctrl+C посреди запроса.

## Этап 5 — Worker pool и доп. функциональность (опционально)
**Цель:** углубить демонстрацию конкурентности и добить UX доски, если останется время.

- [ ] Buffered channel как очередь задач + fixed pool воркеров
- [ ] Worker pool завершается через общий graceful shutdown (Этап 4): при сигнале останова воркеры дорабатывают/сливают текущие задачи, а не обрываются на середине — тот же `context.Context`, что и у HTTP/WS
- [ ] Пример задачи: отправка email-уведомления о приглашении на доску
- [ ] `errgroup` для управления ошибками группы горутин
- [ ] Тест на worker pool (проверка, что все задачи обработаны, нет утечек горутин)
- [ ] Разрешение конфликтов при одновременном редактировании карточки (version field / optimistic locking)
- [ ] Метки/теги на карточках, дедлайны

**Результат:** есть отдельный переиспользуемый механизм фоновой обработки; доска умеет чуть больше, чем голый MVP.

---

## Этап 6 — Роли и права доступа (опционально)
**Цель:** перейти от единой роли MVP к целевой модели (владелец /
участник) из vision.md, если останется время после Этапов 0-5.

- [ ] Middleware/service-проверка: только `owner_id` доски может её
      удалить и приглашать/исключать участников
- [ ] Участник без права владельца по-прежнему может полноценно
      работать с карточками/колонками (это не меняется)
- [ ] Тесты на service-слой: попытка недопустимого действия от
      не-владельца возвращает 403, а не тихо игнорируется
- [ ] Фронт: скрыть/задизейблить действия, недоступные не-владельцу

**Результат:** доска различает владельца и участника; ролевая модель
из vision.md реализована полностью — до этого этапа MVP сознательно
работал с одной ролью (см. Этап 2).

**Осознанно не делаем сложнее.** Гранулярный RBAC (права на уровне
отдельных карточек, кастомные роли и т.п.) остаётся вне проекта
навсегда, независимо от Этапа 6 — см. vision.md, "Что НЕ входит".

## Как пользоваться этим файлом

- Отмечайте пункты `[x]` по мере готовности, коммитьте вместе с кодом
- Если в процессе понимаете, что порядок/состав этапа не подходит — правьте файл, это рабочий документ, а не высеченный в камне план
- Не обязательно проходить всё до Этапа 6 перед тем, как показывать проект на собеседованиях — Этапы 0–4 уже дают полноценный демонстрируемый pet-проект; Этапы 5-6 опциональны и не обязаны идти по порядку между собой
- Идеи вне текущего скоупа (сбор вакансий, AI-классификация) — в `future-ideas.md`, не в этом файле
