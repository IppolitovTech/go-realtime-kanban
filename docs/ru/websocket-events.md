# WebSocket-события

Формат событий реального времени (Этап 3 roadmap.md). OpenAPI 3.0
(`openapi.yaml`) не описывает WS-каналы, поэтому формат зафиксирован
отдельно здесь, а не в `openapi.yaml`.

См. также `architecture.md`, раздел "Роль REST vs WebSocket": WS —
однонаправленный push-канал уведомлений (сервер → клиент). Клиент
никогда не отправляет команды через WebSocket — только REST. Хаб не
содержит бизнес-логики: он лишь рассылает то, что ему передал
REST-хендлер/сервис после успешного изменения.

## Подключение

```
GET /api/v1/boards/{boardId}/ws
```

Апгрейд до WebSocket через тот же `DevUserIdHeader`, что и у REST
(`X-User-ID`, см. `openapi.yaml` — Этап 2 заменит его на реальную
проверку токена без изменений в формате событий). Подключение
проверяет членство пользователя в доске тем же способом, что и
`GET /boards/{boardId}` — не участник доски получает отказ хендшейка,
а не открытое, но бесполезное соединение.

Один клиент = одно соединение = одна доска. Открытая в браузере вторая
вкладка с той же доской — это второе, независимое соединение.

## Формат конверта

Каждое сообщение от сервера — JSON-объект:

```json
{
  "type": "card.moved",
  "board_id": "5f2c1e3a-...",
  "data": { "...": "..." },
  "occurred_at": "2026-08-28T10:15:00Z"
}
```

- `type` — тип события, см. таблицу ниже
- `board_id` — доска, к которой относится событие (совпадает с
  `{boardId}` из URL подключения; поле присутствует для единообразия
  форматов и на случай, если в будущем один сокет будет обслуживать
  несколько досок)
- `data` — полезная нагрузка, форма зависит от `type` (см. ниже);
  специально совпадает по полям с соответствующим REST-ответом
  (`cardResponse`/`columnResponse` в `openapi.yaml`), чтобы фронт мог
  парсить оба канала одним и тем же кодом
- `occurred_at` — время события на сервере, RFC 3339 (UTC)

## Каталог событий

| `type`            | `data`           | Когда отправляется |
|--------------------|------------------|---------------------|
| `column.created`   | `ColumnPayload`  | `POST /boards/{boardId}/columns` создал колонку |
| `column.updated`   | `ColumnPayload`  | `PATCH /columns/{id}` изменил заголовок |
| `column.deleted`   | `ColumnPayload`  | `DELETE /columns/{id}` — снимок колонки на момент удаления |
| `column.moved`     | `ColumnPayload`  | `PATCH /columns/{id}/move` — новый `order_num` уже применён |
| `card.created`     | `CardPayload`    | `POST /columns/{columnId}/cards` создал карточку |
| `card.updated`     | `CardPayload`    | `PATCH /cards/{id}` изменил заголовок/описание |
| `card.deleted`     | `CardPayload`    | `DELETE /cards/{id}` — снимок карточки на момент удаления |
| `card.moved`       | `CardPayload`    | `PATCH /cards/{id}/move` — новые `column_id`/`order_num` уже применены |

`ColumnPayload`:

```json
{
  "id": "uuid",
  "board_id": "uuid",
  "title": "string",
  "order_num": 1.5,
  "created_at": "RFC3339"
}
```

`CardPayload`:

```json
{
  "id": "uuid",
  "column_id": "uuid",
  "title": "string",
  "description": "string",
  "order_num": 1.5,
  "author_id": "uuid",
  "created_at": "RFC3339"
}
```

## Что сознательно не входит в Этап 3

- **События уровня доски** (`board.updated`, приглашение участника) —
  не рассылаются. Основная демонстрация Этапа 3 — синхронизация колонок
  и карточек между вкладками; переименование доски/список участников
  можно добавить тем же способом позже, если понадобится
  (см. `future-ideas.md`)
- **Подавление эха** (не показывать вкладке её же собственное
  изменение) — не реализовано. Клиент, инициировавший REST-изменение,
  и так уже применил его результат из ответа REST-запроса; повторное
  применение того же события, пришедшего по WS, идемпотентно (то же
  состояние переприсваивается), так что усложнение ради этого не
  оправдано на масштабе pet-проекта
- **Переподключение с накоплением пропущенных событий** — при разрыве
  соединения фронт переподключается и просто перечитывает доску целиком
  (`GET /boards/{boardId}`) вместо восстановления пропущенных событий
  из очереди — проще и не требует хранить историю событий на сервере

## Heartbeat

Каждые 30 секунд сервер отправляет WebSocket ping и ждёт pong не более
10 секунд; не дождавшись — закрывает соединение и удаляет клиента из
хаба. Это внутренний механизм хаба (см. ADR 002), фронту реагировать на
него не нужно — библиотека браузера отвечает на ping автоматически.
